# Documentation standard

One idea per page, one place per fact, every number traceable to a record. Status lives in Linear; the repo holds evidence.

## 1. Where things live

| Page | Holds | Never holds |
|---|---|---|
| [MILESTONES.md](MILESTONES.md) | one screen: the hazards before the next real flight, where each Linear project is (last result, next issue, blocked by), links | procedures, history, numbers without a record link |
| [projects/HTX-R1.md](projects/HTX-R1.md) · [HTX-R2.md](projects/HTX-R2.md) · [HTX-R3.md](projects/HTX-R3.md) | one page per Linear project: every milestone and every issue, results tables and figures, evidence links inline | status that is not derived from a record; procedures (link RUNBOOK) |

| `record/<run>_record.md` + `record/<run>/` | one record per test run, written by the tooling; the artefacts behind it | hand-edited numbers |
| `record/figures/` | figures that pages embed, regenerated by `tools/make_figures.sh` | figures made by hand |
| [PX4_MSGS_AUDIT.md](PX4_MSGS_AUDIT.md) | the PX4 message audit (iron rule 5) | — |

## 2. Names come from Linear

[plans/2026-10-26-project-plan-linear.md](plans/2026-10-26-project-plan-linear.md) is the naming authority. Project names (HTX-R1/R2/R3), milestone codes and names (S1…S10, S5b, S5c; R1, M2…M7; L0…L5), issue ids and titles (NEAR-nnn) are copied from it verbatim, typographic apostrophes included. The checker's `linear-parity` pass fails the build on any title that differs. Every page states its `Linear snapshot: <date>`. Status, order and target dates are read in Linear, never maintained here; when Linear changes, the plan file is re-exported and the snapshot date bumped.

## 3. The shape of a milestone

```
### <code> <name> — SIM ONLY (Isaac) | REAL DRONE | DESK
Linear: <status> · <progress> (snapshot <date>) · last ledger row #<n>
Done when (Linear, verbatim): …
| Issue | Title (Linear, verbatim) | Result | Evidence |
<results table and figure for each issue that has data, evidence links inline>
Open: <one line>. Re-run: <one command>.
```

Milestone, then its issues, then the results of those issues. Evidence sits beside the result it supports; there is no separate evidence section.

## 4. Cells

- **Result** holds only a record's verdict word, the headline number and the date, and is filled only when a record exists (`docs/record/*_record.md`, `localisation/results/*_record.md`, or a LEDGER row). Otherwise `—`. Never "done", never a percentage, never copied from Linear.
- **Evidence** links the record and names the LEDGER rows. A path with spaces is written as code, not a link.
- **"Done when"** is Linear's target, printed on its own line and labelled as a target. It is never evidence that anything happened; only the Result and Evidence cells say what happened.
- **Hand-flown results** (teleop, gamepad, any flight a person steered) count only with a link to a video the owner has watched. No video, no result.
- **Scope line:** every results block opens with one sentence saying what was in the loop (which position source flew the drone, which world) and what was not (for example "camera and cuVSLAM not running"). Nobody should have to infer what a test measured from its name; the hover + step test is a control-loop check, not a perception test, and the page says so.
- No status column anywhere. No status pills.
- Negative and superseded results stay in the table.
- Every figure has a numbered caption in italics right under it, 2–4 sentences and at most 400 characters: what is plotted and on which axes, what each line, band and mark means, then the generating command and the ledger rows. The reading of the figure (what it shows, what good looks like, the caveat) is 2–3 sentences of results text above the figure, never in the caption.
- Figures are numbered in page order, `Figure 1` first. The line before the image is `<a id="fig-N"></a>`, and every mention in the text is a link to that anchor (written as `[Figure N]` followed by `(#fig-N)`) so a reader can jump to it. Enforced by `figure-refs`, caption length by `page-budgets`.

## 5. Budgets (enforced by `page-budgets`)

| Page | Limit |
|---|---|
| MILESTONES.md | 60 lines |
| each project page | 250 lines; each `###` milestone 40 lines (figure and caption lines excluded) |
| any table cell on those pages | 120 characters, except the verbatim Linear title column |

Longer than that: it belongs in a record file with a link.

## 6. Wording

- Say "motion-capture positioning (mocap)", never "under mocap". Linear titles are copied verbatim even where they break this.
- No status pills, no "not committed", no "autopilot". American "localization" in new prose; Linear's "Localisation" stays in titles.
- Sim and real are impossible to confuse: the tag in every milestone heading, a SIM/REAL column in every table that could mix them, and the words "observed" / "archived" (never "validated", "PASS", "done") for anything from the previous software.
- Nothing may read as validated on the real drone that was not (iron rule 9).

## 7. After a test run

1. Run the test with its ledger number and issue: `LEDGER=<next #> ISSUE=NEAR-nnn tools/sim_hover_step_run.sh all <new_run_name>`.
2. The record lands in `docs/record/`. Paste its drafted one-line row into [LEDGER.md](record/LEDGER.md) table 1 (append; never edit older rows).
3. Fill the issue's Result cell on the project page from the record (verdict word, headline number, date) and link the record in Evidence.
4. If a figure should change, edit the run list in `tools/make_figures.sh` and run it by hand. Figures never regenerate silently.
5. `tools/docs_check/check_docs.sh` must print `0 FAIL`. The pre-commit guard runs it for you.
6. Commit in the live clone on `main`. Subject: `<project>/<milestone> NEAR-nnn: <what>`. Then pull the mirror; the owner pushes.
7. In Linear: comment the ledger number and record link on the issue, then tick it.

## 8. Structural changes

Moving a section, adding a page, changing a page's shape or the checker's rules is a project, not an edit. It runs through the quality-change process (the `quality-change` skill): size it, convene the review panel, write the design under `docs/superpowers/specs/`, plan under `docs/superpowers/plans/`, execute task by task with a reviewer per task, final whole-branch review, one fix wave, then the acceptance test: an engineer new to the repo answers "what passed, with numbers", "what is next and what must be true first", and "sim or real" from MILESTONES.md plus one click.
